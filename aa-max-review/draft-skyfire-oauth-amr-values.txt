           Additional Authentication Method Reference Values
                 draft-skyfire-oauth-amr-values-latest

Abstract

   The JWT "amr" (Authentication Methods References) claim contains
   values conveying authentication methods used in the authentication.
   This specification defines additional Authentication Method Reference
   values beyond those already registered to represent additional
   authentication methods in use today.

1.  Introduction

   The JWT [RFC7519] "amr" (Authentication Methods References) claim
   [OpenID.Core] contains values conveying authentication methods used
   in the authentication.  They are registered in the IANA
   "Authentication Method Reference Values" registry [IANA.AMR].

   Since the Authentication Method Reference Values [RFC8176]
   specification was published, several new authentication methods have
   been developed and/or come into widespread use.  This specification
   defines additional Authentication Method Reference values to
   represent these additional authentication methods in use today.

   While these Authentication Method Reference values are general
   purpose and can be used in any JSON Web Token (JWT) [RFC7519], one
   use case for them is use in KYAPay tokens
   [I-D.skyfire-oauth-kyapay-token].

3.  Authentication Method Reference Values

   The following Authentication Method Reference values are defined by
   this specification:

3.1.  "app" (Authenticator App) Method

   app:
      Use of an authenticator application on a device held by the user.
      An issuer includes this value where it knows that an authenticator
      application was used.  Where a code is produced from a shared
      secret and the issuer cannot determine what produced it, this
      value is omitted.

3.2.  "bg" (Background Authentication) Method

   bg:
      Background Authentication (Silent network authentication of phone
      number, device recognition, geo-location, etc.)

      The "sna" value (Section 3.3) identifies one specific background
      method and is a subset of this value.  Geo-location is separately
      registered as "geo" and device recognition is within the scope of
      "rba", both in [RFC8176].

3.3.  "sna" (Silent Network Authentication) Method

   sna:
      Silent Network Authentication.  Confirmation by the mobile network
      operator that the device making the request holds the subscriber
      identity associated with a given telephone number, performed
      without any interaction with the user.

3.4.  "email" (E-mail Channel) Method

   email:
      Use of e-mail as the channel by which an authentication
      interaction reached the user.  What was delivered over the channel
      is described by an accompanying value such as "code" or "url".
      See Section 5.

3.5.  "code" (Code provided to and entered by user) Method

   code:
      Code provided to and entered by user

3.6.  "url" (URL provided to and clicked on by user) Method

   url:
      URL provided to and clicked on by user

3.7.  "push" (Push notification to mobile phone) Method

   push:
      Push notification to mobile phone

3.8.  "facliv" (Facial Liveness Check) Method

   facliv:
      Determination that a facial image or video presented for
      authentication is of a live person rather than an artifact such as
      a photograph, mask, or synthetic rendering.  This is a
      presentation attack detection measure [ISO30107-1].

      The "facliv" and "face" [RFC8176] values describe different
      determinations and are not alternatives: "face" is a comparison of
      a presented face against a reference, and "facliv" is a
      determination that the presented face is live.  Where both were
      performed, both values are included.

3.9.  "passkey" (Passkey) Method

   passkey:
      A passkey, that is, a client-side discoverable credential as
      defined by [WebAuthn].

3.10.  "uv" (User Verification) Method

   uv:
      User verification.  Local authorization of the authenticator by an
      authorization gesture capable of distinguishing individual users,
      such as a PIN, a password, or biometric recognition [WebAuthn].

      This is distinct from "user" [RFC8176], which is a test of user
      presence.  As [WebAuthn] states, a user presence test "is not
      capable of biometric recognition, nor does it involve the
      presentation of a shared secret such as a password or PIN".

      This value does not identify which modality the authenticator
      used.

4.  Updated Authentication Method Reference Value

   The following Authentication Method Reference value is updated by
   this specification:

4.1.  "tel" (Telephone Call) Method

   tel:
      Telephone call to the user at a registered number.  The call may
      be used to provide information to the user, such as a code, that
      is then used in another channel.  The call may be used for the
      user to provide information that the caller uses in the
      authentication.

   This definition replaces the one in [RFC8176], which is "Confirmation
   by telephone call to the user at a registered number.  This
   authentication technique is sometimes also referred to as 'call back'
   [RFC4949]."

5.  Composing Authentication Method Reference Values

   The "amr" claim value is an array, and as described in [RFC8176], all
   the applicable values may be returned.  A single authentication event
   is frequently described by more than one value, because the
   registered values describe different aspects of it.

   Two of the values registered by this specification describe the
   channel by which an authentication interaction reached the person:
   "email" and "push".  [RFC8176] registers "sms" and "tel" in the same
   sense, and uses the term "channel" in this sense in its definition of
   "mca".

   Two describe the challenge delivered over such a channel, which the
   person must return to the verifier to complete the authentication:
   "code" and "url".  The person may return it directly, as when a code
   is read and typed in, or indirectly, as when following a link causes
   the value to be sent.  The "otp" value [RFC8176] describes a one-time
   password, whether it is sent to the user or generated by an
   authenticator.

   A channel value alone does not say what the person did.  A challenge
   value alone does not say how it reached them.  An issuer that knows
   both will typically return both.  Appendix A gives examples, and
   Appendix B maps terms in common industry use onto the corresponding
   sets of values.

   The "sms" value registered by [RFC8176] predates this distinction.
   Its definition describes both a channel and the interaction carried
   over it, and is unchanged by this specification.  An issuer wishing
   to be explicit about what was delivered over the SMS channel may
   return a challenge value alongside it.

Appendix A.  Examples

   The following "amr" claim value indicates that a code was sent to the
   user over the e-mail channel and entered by the user:

   "amr": ["email", "code"]

   The following "amr" claim value indicates that a link was sent to the
   user over the e-mail channel and followed by the user:

   "amr": ["email", "url"]

   The following "amr" claim value indicates that a one-time password
   was generated by an authenticator application and entered by the
   user:

   "amr": ["app", "otp"]

   The following "amr" claim value indicates that a password was used
   together with a code sent over the e-mail channel, and that the
   issuer considers the combination to be multiple-factor
   authentication:

   "amr": ["pwd", "email", "code", "mfa"]

Appendix B.  Common Compositions

   The terms below are names in common industry use for authentication
   arrangements that this specification describes using more than one
   value.  This mapping is non-normative.  It is provided so that
   implementers of the same arrangement emit the same set of values.

   Email one-time code, also called email OTP:
      ["email", "code"]

   Magic link, also called e-mail link sign-in:
      ["email", "url"]

   SMS one-time code:
      ["sms", "code"].  As noted in Section 5, "sms" predates the
      channel and challenge distinction, and ["sms"] remains correct.

   Voice one-time code, where a call conveys a code that the user
   then enters:
      ["tel", "code"]

   Call-back confirmation, where the user confirms during the call
   itself:
      ["tel"]

   Authenticator application one-time password:
      ["app", "otp"]

   Push approval:
      ["push"]

   Push approval with number matching:
      ["push", "code"]

   Silent network authentication:
      ["sna"]

   Facial recognition with a liveness check:
      ["face", "facliv"]

   Device-bound passkey held in hardware, such as on a security key:
      ["passkey", "hwk"]
